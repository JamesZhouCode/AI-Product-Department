# 产业链智能体方案（v1）

> 目标：把现在「脚本 + 静态分片 + 本地问答」的形态，升级成一套**能按人给的思路自我改进采集、能有序沉淀数据、能回答产业链问题**的智能体系统。
>
> 设计原则（延续仓库既有约定）：
> 1. **证据优先**：每条事实都带 `evidence_id`、来源 URL、抓取时间、置信度；查不到就留白，不填造值。
> 2. **数值不交给模型**：回答里的家数、占比、名单一律由工具（SQL/图查询）算出，模型只负责组织语言。
> 3. **前端运行时不外调**：地图、图谱、周报仍只读 `public/data` 分片，由「发布器」从库里导出，契约不变。
> 4. **人在环上**：智能体可以提方案、跑预算内的活，但改口径、放宽来源、扩大抓取范围必须人工点头。

## 2. 目标形态：一个智能体，三种能力

```
                    ┌──────────────────────────────┐
   人的指引 ───────▶ │  策略卡 / 审批台 / 评测金标    │
                    └──────────────┬───────────────┘
                                   ▼
   ┌──────────────────────────────────────────────────────────┐
   │  采集智能体（Diagnose → Plan → Approve → Act → Verify → Learn）│
   └───────┬──────────────────────────────┬───────────────────┘
           ▼                              ▼
   ┌───────────────┐              ┌────────────────┐
   │ 采集执行层      │              │ 数据底座        │
   │ 渠道/解析/限速  │─────────────▶│ ODS→DWD→DWS    │
   └───────────────┘              │ + 证据 + 版本   │
                                  └───────┬────────┘
                                          ▼
                                  ┌────────────────┐
                                  │ 知识层（切片/向量）│
                                  └───────┬────────┘
                                          ▼
                                  ┌────────────────┐
                                  │ 问答智能体（工具调用）│
                                  └────────────────┘
```

1. **会改进采集**：每轮先诊断「哪里缺、缺多少」，提补采计划，人审批后执行，用「新增有效企业数/请求数」给策略打分，下一轮优先用高收益策略。
2. **会存储**：原始件进对象存储，解析结果进 Postgres，成品按快照发布为现有 JSON 分片；每条数据可追到源文件和原文位置。
3. **会答问**：意图路由到工具（统计算数、企业检索、图谱邻居、文档检索），答案带引用，没证据就明确说不知道。

## 3. 智能体核心：六步闭环

每一轮采集是一次「有记忆的实验」，而不是一次性的脚本执行。

### 3.1 Diagnose（诊断缺口）

自动产出的缺口信号（全部可用 SQL 算）：

| 信号 | 判据 | 说明 |
| --- | --- | --- |
| 环节稀疏 | 某二级环节企业数 < 同层中位数 40% | 可能是漏采或环节定义过窄 |
| 区域空白 | 某省企业数占比 < 该省制造业占比的 1/3 | 属地覆盖不足 |
| 画像缺失 | 无主营产品 / 无地址占比 > 15% | 解析器或来源质量差 |
| 关系稀疏 | 环节间关系密度 < 0.3 条/家 | 供应链披露没抓全 |
| 名单漂移 | 与权威名单（CNESA、工信部）比对缺 X 家 | 最硬的召回缺口 |
| 时效超期 | 最近更新 > SLA（公告 T+1、招投标 T+3、财报 T+7） | 增量任务没跑 |

产出：`gap_report`（JSON），每条带证据与建议动作类型。

### 3.2 Plan（提补采计划）

把缺口翻译成**可执行动作**，四类：

- `source:add` 新增渠道（如中国化学与物理电源行业协会名单页）
- `query:expand` 扩充检索词（由模型按环节生成候选词，附理由，需人审）
- `parser:fix` 修解析器（某站改版、某类 PDF 表头变化）
- `entity:merge` 主体合并（别名/曾用名待审队列）

每条动作附：预计新增企业数、预计请求量、合规风险（robots/频控/授权）、回滚方式。

### 3.3 Approve（审批）

- **预算内 + 低风险**（只读公开页、请求量在配额内）：自动执行，事后出报告。
- **超预算 / 涉及授权数据 / 改口径**：进审批台，人点通过。
- 审批记录进 `decision_log`，成为智能体的「程序性记忆」。

### 3.4 Act（执行）

任务队列（Redis + worker）执行，统一封装：限速、robots 检查、重试退避、缓存（同 URL 24h 内不重复抓）、断点续跑。

### 3.5 Verify（校验）

每批结果必须过闸：

- 主体：有统一社会信用代码或可解释的合并依据，否则进 `pending_merge`；
- 字段：关键字段（环节、地区、上市标记）必须有证据，置信度低于阈值进人工队列；
- 抽样：每批随机 20 家人工核验环节归属，准确率 < 95% 则整批回退并告警；
- 去重：与既有主体相似度 > 0.92 的进合并待审，不自动合并。

### 3.6 Learn（记忆与策略进化）

- **源卡片**（semantic memory）：每来源记录 `robots`、限速、解析难度、历史命中率、最近失效时间。
- **情景记忆**（episodic）：每轮 `run_id` 的诊断、动作、结果、成本，可回放。
- **策略权重**：按 `有效新增企业数 / 请求数` 用 Thompson 采样给策略打分，下一轮优先高收益动作；连续 3 轮零收益的策略自动降权并标记可疑。

> 这就是「按你的思路不断优化」的落点：**你给的是策略卡（先抓谁、用什么词、什么算合格），智能体负责试、记账、择优。**

## 4. 数据存储设计

### 4.1 分层

| 层 | 存什么 | 介质 | 保留策略 |
| --- | --- | --- | --- |
| ODS 原始层 | HTML / PDF / XLSX 原文 + HTTP 头 + 内容哈希 | 对象存储（MinIO/S3） | 全留，按 `source/yyyy-mm/` 归档 |
| DWD 明细层 | 企业、别名、环节标签、关系、证据 | Postgres | 全留 + 版本 |
| DWS 汇总层 | 环节家数、地区分布、分层结果 | Postgres 物化视图 | 随明细刷新 |
| 知识层 | 政策/研报/公告切片 + 向量 | Postgres + pgvector | 按文档版本 |
| 发布层 | 前端分片 JSON | `public/data/industries/*.json` | 每次发布一个快照 |

规模判断：五条链约 1 万家主体、每年 5–10 万份文档，**单机 Postgres 16 + pgvector 足够**，不需要图数据库（关系查询用邻接表 + 递归 CTE）；后续真要做多跳推理再评估 Neo4j。

### 4.2 核心表（简化 DDL）

```sql
-- 主体：统一社会信用代码唯一
create table company (
  id             uuid primary key default gen_random_uuid(),
  credit_code    text unique,
  name           text not null,
  norm_name      text not null,
  company_type   text,                         -- listed / ordinary
  stock_code     text,
  region_province text, region_city text, region_district text,
  address        text, lng numeric, lat numeric, geo_precision text,
  profile        jsonb,                        -- 主营/产品/核心技术（带字段级证据）
  first_seen_at  timestamptz not null default now(),
  updated_at     timestamptz not null default now()
);

create table company_alias (
  company_id uuid references company(id),
  alias      text not null,
  alias_type text,                             -- 简称/曾用名/品牌/英文名
  evidence_id text,
  primary key (company_id, alias)
);

-- 环节标签：多对多，但只有一个主环节
create table company_chain_tag (
  company_id   uuid references company(id),
  industry_code text not null,                 -- ES / IC / CP
  level1       text not null,
  level2       text not null,
  is_primary   boolean not null default false,
  confidence   numeric,
  evidence_id  text,
  assigned_by  text,                           -- rule / llm / manual
  assigned_at  timestamptz default now(),
  primary key (company_id, industry_code, level2)
);

create table relation (
  id           bigint generated always as identity primary key,
  industry_code text not null,
  from_company uuid references company(id),
  to_company   uuid references company(id),
  rel_type     text not null,                  -- 供应 / 经销 / 股权
  confidence   numeric,
  evidence_id  text,
  valid_from   date, valid_to date
);

create table evidence (
  id         text primary key,
  doc_id     text references raw_document(id),
  locator    text,                             -- 页码/表格行/段落锚点
  quote      text,
  source_url text,
  fetched_at timestamptz
);

create table raw_document (
  id           text primary key,               -- sha256
  source_id    text not null,
  url          text,
  http_status  int,
  content_hash text,
  storage_key  text not null,                  -- 对象存储路径
  fetched_at   timestamptz not null,
  parser       text,
  parse_status text                            -- ok / partial / failed
);

-- 知识层
create table doc_chunk (
  id            bigint generated always as identity primary key,
  doc_id        text references raw_document(id),
  industry_code text,
  chunk_no      int,
  content       text not null,
  embedding     vector(1024),
  meta          jsonb,                         -- 文档类型/发文机关/生效日/数据窗口
  unique (doc_id, chunk_no)
);
```

### 4.3 三个关键约定

1. **一条事实一条证据**：`company_chain_tag.evidence_id` 必填（除人工覆盖），前端详情页可回显「依据：某招标公告第 3 页」。
2. **时间与口径版本**：所有事实带 `fetched_at` / `valid_from` / `data_window`，跨期查询默认「最新可用」，比较类查询强制同窗口。
3. **发布即快照**：`export-snapshot.mjs` 从库导出与 `docs/data-schema.md` 完全一致的 JSON，写 `snapshot_id` 到 `index.json`；前端零改动，可随时回滚到上一快照。

## 5. 采集执行层

- **渠道注册表**（`source` 表）：`id / 名称 / 类型（名单/招投标/公告/工商/协会）/ 入口 URL / 频率上限 / 是否需要授权 / 解析器`。
- **四类渠道的固定套路**（来自思维导图，直接固化为策略卡）：
  1. 权威名单优先（CNESA、电池工业协会、工信部规范名单）；
  2. 项目反推（招标公告 → 中标企业 → 设备供应商）；
  3. 资本市场反推（年报/招股书「前五大供应商」）；
  4. 工商关键词（名称/经营范围 → 长尾补齐）。
- **解析**：先规则（表格定位、正则），失败再交给模型做「HTML/PDF → 指定 JSON Schema」的结构化抽取，Schema 校验不过直接丢弃并记失败样本。
- **增量**：列表页按 `last_modified` / 发布日期滚动抓；文档按内容哈希去重；已解析过的 URL 记 `parse_status`，不重复消耗模型额度。

## 6. 问答层

### 6.1 路由与工具

| 意图 | 工具 | 数据来源 |
| --- | --- | --- |
| 家数、占比、分布 | `chain_stats` | DWS 物化视图 |
| 某企业是谁 | `company_lookup` | company + alias + tag |
| 某环节有哪些企业 | `list_companies` | company_chain_tag |
| 上下游/股权关系 | `graph_neighbors` | relation（递归 CTE） |
| 政策/研报怎么说 | `search_docs` | doc_chunk 向量检索 |
| 建链方法 | `search_docs`（方法论文档） | 思维导图 + 方案文档 |

### 6.2 生成约束

- 回答中的**每个数字必须来自工具结果**，模型只做归纳与措辞；
- 强制引用：`[企业:uuid]`、`[文档:doc_id#p3]`，前端可点开原文；
- 无检索结果 → 明确拒答 + 给出可问范围（延续现在「如实留白」的风格）；
- 流式输出（SSE），首字延迟控制在 1.5s 内；断网/超额自动回退到本地规则引擎。

### 6.3 评测

- 金标集 100 题（事实类 60 / 方法类 20 / 跨链对比 10 / 应拒答 10），每次改 prompt 或换模型跑一遍；
- 指标：数值一致率 ≥ 98%、引用命中率 100%、应拒答准确率 ≥ 90%、平均时延 < 4s。

## 7. 与现有仓库的衔接

- **不破坏前端契约**：新增 `export-snapshot.mjs`，产物仍写 `frontend/public/data/industries/*.json`；`pnpm prepare:*` 保留，逐步把数据源从 Excel 换成数据库导出。
- **服务边界**（符合 `AGENTS.md` 的 `backend/` 规划）：
  - `backend/`（Spring Boot）做对外网关：鉴权、限流、`/api/assistant/chat`、`/api/chain/stats`；
  - `agent/`（Python，FastAPI + worker）做智能体与采集，仅内网访问；
  - 前端只调网关，不直连抓取服务。
- **渐进式改造**：`ChainAssistantPage` 增加 `fetch('/api/assistant/chat')` 分支，后端不可用时自动用现有 `assistantBrain.js`，演示环境无需任何服务也能跑。
- **单人可跑**：`docker compose up` 起 Postgres + MinIO + Redis + worker + api；本地开发用 SQLite 兼容层不现实，直接用 Docker 的 Postgres 即可。

## 8. 落地路线

| 阶段 | 交付物 | 验收标准 |
| --- | --- | --- |
| **P0 数据底座** | Docker Compose（PG/MinIO/Redis）、六张核心表、把 `prepare-*` 脚本改为可重跑任务、`export-snapshot.mjs` | 现有五条链能完整入库并原样导出，前端 diff 为空；任取一家企业能追到原始文件与页码 |
| **P1 采集智能体 v1** | 缺口诊断器、策略卡、审批台（简单页面）、任务执行器、源卡片与 run 日志 | 对储能链跑一轮：自动给出 ≥ 10 条缺口动作，执行后有效新增企业可量化；重复率 < 1% |
| **P2 知识层与问答** | 文档切片与向量化、工具集、SSE 问答接口、前端接入 + 本地兜底 | 金标 100 题准确率 ≥ 85%，每条回答可点开引用；断网时自动回落本地引擎 |
| **P3 持续优化** | 策略权重（Thompson）、覆盖率看板、时效告警、评测回归 | 连续 4 周覆盖率单调不降；告警到人；每次发布都有评测报告 |

## 9. 风险与合规

| 风险 | 应对 |
| --- | --- |
| 抓取合规 | 只采公开页面，遵守 robots 与频控；不采个人信息；需授权的数据源走 API 合同 |
| 模型幻觉 | 数值走工具、引用强制、Schema 校验、抽样人工核验 |
| 数据污染 | 默认不自动合并主体；低置信度进人工队列；发布前跑审计脚本 |
| 成本失控 | 只对「内容哈希变化」的文档跑模型；抽取用小模型，问答用大模型；每轮任务设预算上限 |
| 口径漂移 | 数据窗口 + 快照版本；跨期比较强制同窗口 |
| 单点依赖（某站改版） | 解析器健康检查：连续 3 次解析失败自动降级并告警 |

## 10. 需要拍板的五个决策点

1. **数据源授权**：除公开页面外，是否采购企查查/天眼查 API？（决定 P1 的召回上限）
2. **模型选型**：内部私有化（Qwen/DeepSeek 本地部署）还是走平台云服务免密钥？（决定合规与成本）
3. **主体唯一键**：非上市小微很多没有信用代码，是否接受「名称+地区」作为弱主键并标注置信度？
4. **问答边界**：只答链内数据，还是允许模型补充行业常识（需明确标注「非链内数据」）？
5. **上线形态**：先做内部演示（单机 Compose），还是直接进内网环境（需要 DBA、对象存储、网关资源）？

## 附：最小可行切片（先跑通一条链）

不追求一次做完，先拿**储能链**跑通一条竖线：

```
抓 1 个权威名单（CNESA） → 落 ODS → 规则解析入库 → 与现有 1,977 家比对出缺口
→ 针对缺口跑 1 个补采策略（招投标反推）→ 校验入库 → 导出分片对比前端
→ 问答问「新补了多少家、在哪个环节」→ 引用到公告原文
```

这条竖线打通后，其余渠道只是「注册表里再加一行」，智能体的诊断/审批/记忆机制不用改。
